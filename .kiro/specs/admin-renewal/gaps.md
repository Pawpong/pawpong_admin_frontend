# 관리자 리뉴얼 · API gap

기준일: 2026-09-05. 개발 서버 `https://dev-api.pawpong.kr/docs-json`과 로컬 백엔드 `f6aa6f75`의 swagger.json을 비교했다. 당시 두 명세는 동일했다. 이후 배포 변경은 `pnpm test:contract:update && pnpm test`로 다시 확인해야 한다.

## 구현 범위

관리자 API 119개 전체에 프런트엔드 호출 코드를 연결했다. 중복 래퍼 및 공용 v2 업로드·로그아웃을 포함한 호출 지점 131개를 검사한다. [API 목록](./api-coverage.md).

새 화면: 인기 검색어 CRUD, 시스템 상태, 알림 이력·통계, 커뮤니티 신고 처리, 이메일 6종 미리보기·테스트 발송, 콘테스트 상태 변경. 기존 브리더 화면에 서버 선정 대상자 일괄 서류 독촉을 추가했다. 파일 폴더 조회·전체 삭제와 공지사항 상세 조회도 실제 API에 연결했다.

수정: 관리자 토큰 갱신 경로·응답, 동시 401 갱신 중복 방지, 로그아웃 중 갱신 응답에 의한 세션 복원 방지, v2 업로드·로그아웃, 탈퇴 사용자 limit, 신고 상태 resolved/dismissed, 화이트리스트 total, 팝업 공지 전체 페이지 조회, 실제 배너·업로드 응답 타입.

## 백엔드 기능 gap

| 항목 | 현재 제공 범위 | 남은 기능 |
|---|---|---|
| 콘테스트 관리 | 항목 ID로 hidden/deleted 변경 | 관리자 목록·검색·상세·복원 API 없음. 화면은 ID 입력 방식이며 대상 내용을 먼저 조회할 수 없음 |
| 관리자 프로필 | GET /user-admin/profile | 수정·이미지 업로드 API 없음. 존재하지 않던 업로드 버튼 제거, 조회만 제공 |
| 커뮤니티 신고 | 목록, resolve, dismiss | 관리자 게시물 상세 조회 API 없음. 신고 내용과 게시물 ID를 표시 |
| 알림 이력 | 목록·통계 | 재발송·관리자 읽음 변경 API 없음 |
| 이메일 테스트 | 미리보기와 6종 발송 | sent 응답으로 요청 결과 확인. 실제 수신함 도착·스팸 분류는 프런트에서 검증 불가 |
| 스토리지 목록 | isTruncated 응답 | 목록이 잘릴 때 이어받을 continuation token 요청 규격 없음. 대규모 목록의 완전성은 별도 백엔드 확인 필요 |

## 검증 gap · 기술 부채

- 2026-09-06 기존 운영 로그인 세션을 정상 refresh API로 갱신하고 운영 조회 12건을 확인했다(모두 HTTP 200). 프로필, 플랫폼/브리더 통계, 브리더 목록·검색·지역, 시스템 상태, 알림 목록·통계, 인기 검색어, 커뮤니티 신고, 이메일 카탈로그. CRUD 저장, 파일 업로드, 실제 발송, 역할별 거부는 미검증이다. 운영 DB 변경·로그인 우회는 수행하지 않았다.
- 정적 명세 검사는 경로·메서드·알려진 타입 필드·enum을 비교한다. 서버의 비즈니스 로직, 데이터베이스 제약, DTO 밖의 검증까지 보장하지 않는다.
- 기존 코드의 lint 오류가 남아 있다. 최종 실행 기준 18 errors / 1 warning: 기존 데이터 훅의 effect 내 동기 setState, 미사용 변수, UI 파일의 helper 혼합 export, effect 의존성. 처음 발견한 30 errors / 2 warnings에서 스토리지 참조 조회 의존성과 통계의 렌더 중 컴포넌트 선언 등 일부를 수정했다. lint 전체 통과로 보고하지 않는다.
- 2026-09-06 라우트별 lazy loading과 페이지 오류 복구를 적용했다. 최초 JS 청크는 약 828 KB / gzip 270 KB로 감소했다(직전 빌드 약 1,744 KB / gzip 534 KB). 공통 Ant Design 코드가 포함돼 500 KB 경고는 남는다.
- 프로덕션은 `VITE_API_BASE_URL`을 우선 사용하며 미설정 시 `https://api.pawpong.kr/api`를 사용하도록 수정했다. 개발 환경은 Vite `/api` 프록시로 지정된 백엔드에 연결한다. 현재 로컬 override는 localhost:8080이며, 저장소 밖 `.env.development.local`에만 둔다.
- localhost:5175는 기존 백엔드 CORS 목록에서 빠져 있었다. Vite 프록시 적용 후 브라우저에서 실제 401 JSON을 수신하여 Network Error 차단이 해소된 것을 확인했다. 로컬 서버 설정 `.env`는 dev DB를 지정한다. prod 명세도 별도로 받아 131개 호출 / 119개 관리자 API 일치를 확인했다.

## 1차 배포의 계정 구분 필터

사용자가 전달한 후속 계약 accountType=all|normal|test를 브리더 관리/신청 UI 및 API에 연결했다. 배포 명세에 아직 없는 상태이므로 일반/테스트 선택은 기본 비활성이다. 전체는 accountType을 생략해 현재 서버와 호환된다. 백엔드 배포 확인 후 VITE_ACCOUNT_TYPE_FILTER_ENABLED=true로 활성화하고 명세 fixture를 갱신해야 한다. 그 전까지 계약 검사에서 해당 신규 query 필드는 불일치로 보고되며 나머지 119개 관리자 operation 연결은 유지된다.

## 2026-09-06 브리더 관리 고도화

이름/이메일 및 지역 서버 검색, URL에 검색·상태·페이지 저장, 뒤로가기 복원, 필터 변경 시 페이지/선택 대상 초기화를 적용했다. 늦은 목록 응답을 무시하고 실패 시 재시도 버튼을 제공한다. 관리 상세는 목록 복사 대신 상세 API를 조회한다. 일반/테스트 필터는 운영 명세 미반영으로 계속 비활성 상태다.

## 2026-09-06 재점검: 상태 화면 및 중복 심사

운영 `/docs-json` 재검사: 131개 호출, 119/119 관리자 operation 연결, accountType query 1건 불일치 유지.

- **심사 중복 처리 방지 (백엔드 후속 필요)**: 로컬 백엔드 `UpdateBreederVerificationUseCase`는 기존 상태 조건 없이 업데이트하고 승인/반려 알림을 발송한다. 현재 프런트는 완료 상태 작업 버튼을 숨기고, 요청 직전 상세 재조회 및 클릭 잠금으로 중복 처리를 차단한다. 여러 관리자 간 동시 요청을 완전히 차단하려면 서버에서 허용 상태 전이 검증, 기존 상태를 조건으로 한 원자적 업데이트, 중복 발송 방지가 필요하다. 운영에서 변경 요청을 보내 이 문제를 재현하지 않았다.
- **시스템 상태 판정**: Loki 로그 집계 기반이다. `isResolved=true`는 30분간 재발 없음이며 실제 복구 확인이 아니다. 서비스 실시간 probe, 이슈별 로그/trace 상세, 담당자 지정·확인·해결 이력 API가 없다. 화면에서 집계 기준과 조회 시각을 표시하고 ‘해결됨’을 ‘최근 재발 없음’으로 변경했다.
- **집계 완전성**: 로컬 구현상 Loki 조회는 최대 5,000개 로그로 제한된다. 응답에 잘림/수집 실패/조회 건수 메타데이터가 없어 집계 수치를 기간 전체의 확정 건수로 보장할 수 없다.
- 상태 화면 간격: 데스크톱 섹션/서비스 카드 gap 24px, 카드 padding 24px. 모바일 섹션 gap 20px, 서비스 카드 gap/padding 16px. 표 설명·행 padding도 분리했다.
- 심사 UI: pending → reviewing → approved/rejected만 제공한다. approved/rejected/알 수 없는 상태는 조회 전용이다. 반려 후 재신청은 서버가 상태를 변경한 후 심사한다.

## 2026-09-06 신청 상세 · 첨부 · 알림 미리보기

- 상세 API에 있는 상호명, 소개, 경력(0 포함), 최종 수정일, 이메일 제출 여부, 심사 일자 및 반려 사유를 표시한다. 문서 배열 미제공, 빈 배열, 이메일 제출을 구분한다. 처음 사용자가 지목한 로컬 신청은 실제 상세 응답이 pending, documents=[], isSubmittedByEmail=false, submittedAt 없음이었다.
- 첨부 이미지 확대 및 모든 첨부 원본 링크를 제공한다. PDF/확장자 없는 문서는 내부 iframe 뷰어와 새 탭 원본 열기를 제공한다. 브라우저 PDF 지원 여부에 따라 원본 열기를 사용한다. 상세 재조회로 서명 URL을 갱신한다.
- 알림톡 템플릿 API에는 content/body 원문이 없다. 운영 BREEDER_APPROVED/BREEDER_REJECTED GET 각각 200이며 requiredVariables=[]인 것을 확인했다. 템플릿 상세 및 승인 전 확인창/반려 창에 템플릿 코드, 활성·검수 상태, 필수 변수 예시 입력, 버튼 문구·링크 치환을 제공한다. 예시 입력은 저장/발송 요청에 포함하지 않는다.
- 로컬 백엔드 BreederVerificationAdminNotifierAdapter와 NotificationBuilder의 승인/반려 흐름은 서비스 알림·이메일·푸시를 처리하며 AlimtalkService 호출이 없다. 알림톡 서비스에 별도 승인/반려 메서드는 있으나 해당 관리자 흐름과의 연결은 확인되지 않는다. 템플릿 존재를 발송 연동의 증거로 표시하지 않는다.
- 정확한 최종 카카오 메시지 미리보기를 위해 백엔드에 솔라피 원문 조회, 실제 이벤트→템플릿 매핑, 수신자 변수 바인딩과 읽기 전용 render API가 필요하다. 승인 요청에 알림톡 발송을 추가하는 변경은 하지 않았다.
- 검증: 테스트 28개/빌드/변경 파일 lint 통과. 390px에서 신청 내용·0년 경력·이메일 제출 표시·첨부 원본·승인 전 변수 치환 확인, 변경 API 호출 0건.
